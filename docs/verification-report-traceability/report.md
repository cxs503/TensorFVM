# Report traceability: are the numbers we publish still connected to evidence?

Mission m3601 · branch `agent/m3601` · reproduce with
`python3 scripts/audit_report_traceability.py` (writes `traceability.json`,
`claims.json`, `traceability.png`) and gate with
`python3 -m pytest tests/test_report_traceability.py` (8 cases).

## 1. What this is about

TensorFVM quotes measured numbers in **135** `docs/**/report.md` files. Each of
those numbers is a published claim: it is repeated in platform reports, PR
bodies and benchmark comparisons. Nothing in the test suite checked that a
quoted number still agrees with the evidence that produced it, so two silent
failure modes were open:

* a report text is retyped/edited and drifts away from its artifact;
* an artifact is regenerated by changed solver code and the report keeps the old
  number (or the report quotes a `scripts/*.py` that no longer exists).

This case converts "the report quotes what the run produced" into an executable
statement and measures how much of it is actually true today.

## 2. Method

For every `report.md`:

1. **Claimable tokens.** Numeric tokens with >= 3 significant digits and a
   non-trivial mantissa (`1e-10` gates and `48x16x4` mesh sizes are excluded:
   they carry no measured content). Total: **2057** over **132** reports that quote
claimable numbers (135 reports scanned, 3 quote none).
2. **Local provenance (gated).** A token is *locally traced* when a leaf of a
   committed evidence file in the same report directory (`*.json`, `*.dat`,
   `*.csv`, `*.txt`; `config.json`/`environment.json` excluded, they only echo
   inputs) reproduces it within the **printed precision band** = half a unit in
   the last printed decimal place. That band is exact arithmetic, not a
   tolerance knob: `38.9` accepts `[38.85, 38.95]`.
3. **Tree provenance (measured, not gated).** Failing (2), does the number appear
   anywhere in the committed `docs` evidence tree (15341 distinct numbers)?
   Weaker provenance (collision with an unrelated array is possible) but it
   separates "archived elsewhere" from "nowhere".
4. **Reproduce pointers.** Every `scripts/*.py` quoted by a report must exist.
   A bare file name quoted as a name is prose, not a pointer.

`docs/verification-report-traceability/claims.json` freezes the locally traced
claims with their JSON pointers; the test re-verifies doc text **and** artifact
leaf, so either side moving is a red test, and the registry is a ratchet
(claims may grow, never shrink).

## 4. Error judgement against the baseline

There is no physical reference value here; the baseline is the claim itself.

| key quantity | baseline | measured | verdict |
|---|---|---|---|
| locally traced share | 100 % (ideal) | 2.09 % | **not < 3 %** — the gap is large and honest |
| tree-traced share | 100 % (ideal) | 18.13 % | **not < 3 %** |
| dead reproduce pointers | 0 | 0 after fix (1 before) | **< 3 %** ✔ |
| drift detection (negative controls) | must fail on drift | both controls red-on-drift, 8/8 tests green | ✔ |

The audit does **not** claim the physics is wrong: a number with no committed
artifact may still be exactly what the run produced. What is measured is
*provenance*, and the honest answer is that the repository publishes far more
numbers than it archives evidence for. The 81.87 % "nowhere" bucket is dominated
by reports whose only committed artifact is a hash manifest
(`manifest.json` with `source_sha256`/`artifact_sha256`) — the numbers lived in a
run directory that was never committed.

## 5. Notes / limits

* A *locally traced* claim proves agreement of text and committed evidence, not
  correctness of the computation behind it. Bind a claim to a physics reference
  separately (that is what `docs/verification-*` cases do).
* Tree provenance is a numeric-collision test; a common round value could match
  by coincidence, which is why it is reported and not gated.
* Files whose suffix is not in `{.json,.dat,.csv,.txt}` (`.npz`, `.png`) are not
  mined; 3 `.npz` artifacts exist and are currently invisible to the audit.
* The gate only covers reports that already have colocated evidence. Raising the
  gated share requires archiving run outputs next to the report — a per-case
  change, not something this audit can do centrally.

## 6. CI repair: the gate had to survive a checkout it did not write

The first round of this PR was red on `test (3.11)` and `test (3.12)`. All three
defects were in the *gate*, not in the physics:

1. **Machine-bound paths.** `claims.json` froze absolute work-tree paths
   (`.../work/m3601/docs/...`), so the 15 recorded claims resolved only inside
   the work tree that wrote them and `verify_registry` would report
   `doc_missing` on CI. Every recorded path is now repository-relative
   (`portable()`), resolved through `repo_root()` (`resolve()`), and a test
   asserts that no absolute path is recorded.
2. **Self-reference.** The audit scanned its own report directory, so this
   report's own numbers were part of the population it measures (a fixed-point
   problem: editing the report moved the number the report quotes) and the dead
   pointer it documents as a finding was re-counted as a live pointer. The
   directory holding `claims.json` is now excluded (`is_self_report`), and the
   *definition* of a reproduce pointer keeps its `scripts/` prefix — a bare file
   name quoted as a name is prose.
3. **Exact-equality baseline.** `live["claimable"] == SUMMARY["claimable"]` is
   wrong on `pull_request` runs, which check the merge ref (branch **plus**
   main): any mission landing a new report on main reddens this gate without
   touching the branch. The test now ratchets — totals may grow, and every
   *recorded* report is checked individually (it may not lose claimable numbers
   or disappear).

Reproduced failures before the fix (verbatim): `['scripts/verify_two_phase_m2903.py']`
from the dead-pointer gate and `(2062, 1813)` from the equality gate. After the
fix, `python3 -m pytest tests/test_report_traceability.py -q` gives `8 passed`
(CPython 3.11.6), and the record above is regenerated from the merged tree
(`agent/m3601` + `main` at `87d4083`).
