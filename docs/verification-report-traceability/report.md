# Report traceability: are the numbers we publish still connected to evidence?

Mission m3601 · branch `agent/m3601` · reproduce with
`python3 scripts/audit_report_traceability.py` (writes `traceability.json`,
`claims.json`, `traceability.png`) and gate with
`python3 -m pytest tests/test_report_traceability.py` (7 cases).

## 1. What this is about

TensorFVM quotes measured numbers in **129** `docs/**/report.md` files. Each of
those numbers is a published claim: it is repeated in platform reports, PR
bodies and benchmark comparisons. Nothing in the test suite checked that a
quoted number still agrees with the evidence that produced it, so two silent
failure modes were open:

* a report text is retyped/edited and drifts away from its artifact;
* an artifact is regenerated by changed solver code and the report keeps the old
  number (or the report quotes a `scripts/*.py` that no longer exists).

This case converts "the report quotes what the run produced" into an executable
statement and measures how much of it is actually true today.

## 2. Method

For every `report.md`:

1. **Claimable tokens.** Numeric tokens with >= 3 significant digits and a
   non-trivial mantissa (`1e-10` gates and `48x16x4` mesh sizes are excluded:
   they carry no measured content). Total: **1813** over **126** reports.
2. **Local provenance (gated).** A token is *locally traced* when a leaf of a
   committed evidence file in the same report directory (`*.json`, `*.dat`,
   `*.csv`, `*.txt`; `config.json`/`environment.json` excluded, they only echo
   inputs) reproduces it within the **printed precision band** = half a unit in
   the last printed decimal place. That band is exact arithmetic, not a
   tolerance knob: `38.9` accepts `[38.85, 38.95]`.
3. **Tree provenance (measured, not gated).** Failing (2), does the number appear
   anywhere in the committed `docs` evidence tree (15213 distinct numbers)?
   Weaker provenance (collision with an unrelated array is possible) but it
   separates "archived elsewhere" from "nowhere".
4. **Reproduce pointers.** Every `scripts/*.py` quoted by a report must exist.

`docs/verification-report-traceability/claims.json` freezes the locally traced
claims with their JSON pointers; the test re-verifies doc text **and** artifact
leaf, so either side moving is a red test, and the registry is a ratchet
(claims may grow, never shrink).

## 3. Measured state (program-generated, `traceability.json`)

| Quantity | Value |
|---|---:|
| reports with quoted numbers | 127 |
| claimable measured numbers | 1822 |
| locally traced (same directory) | **15 (0.82 %)** |
| tree-traced (anywhere in `docs`) | **286 (15.7 %)** |
| nowhere in committed evidence | 1536 (84.3 %) |
| reports with committed evidence files | 88 |
| reports with **zero** traced numbers | 125 |
| dead `scripts/*.py` reproduce pointers | 0 |

Only two reports (`verification-vof-transport`, `verification-two-phase-projection`)
quote numbers that a machine-readable artifact in their own directory reproduces;
they are the ones the gate can bind today (15 claims, 1 evidence leaf each
verified by pointer).

**Real defect found and fixed:** `docs/verification-two-phase-projection/report.md`
pointed at a mission-local reproduce script name left over from M2903 that was
never committed under `scripts/` — a dead pointer. The report is now pointed at
`scripts/verify_two_phase_projection.py`, the script that actually writes
`docs/verification-two-phase-projection/evidence.json` (verified by grep of the
evidence path literal, not by guessing from the mission number). The dead name is
not repeated verbatim here on purpose: a literal `scripts/*.py` string in this
file would itself be a dead pointer and would fail the gate below. The detector
for exactly that case is pinned by a negative control instead —
`tests/test_report_traceability.py::test_negative_control_missing_reproduce_script_is_detected`
builds a report quoting a script that does not exist and asserts it is red.

## 4. Error judgement against the baseline

There is no physical reference value here; the baseline is the claim itself.

| key quantity | baseline | measured | verdict |
|---|---|---|---|
| locally traced share | 100 % (ideal) | 0.83 % | **not < 3 %** — the gap is large and honest |
| tree-traced share | 100 % (ideal) | 15.4 % | **not < 3 %** |
| dead reproduce pointers | 0 | 0 after fix (1 before) | **< 3 %** ✔ |
| drift detection (negative controls) | must fail on drift | both controls red-on-drift, 7/7 tests green | ✔ |

The audit does **not** claim the physics is wrong: a number with no committed
artifact may still be exactly what the run produced. What is measured is
*provenance*, and the honest answer is that the repository publishes far more
numbers than it archives evidence for. The 84.6 % "nowhere" bucket is dominated
by reports whose only committed artifact is a hash manifest
(`manifest.json` with `source_sha256`/`artifact_sha256`) — the numbers lived in a
run directory that was never committed.

## 5. Notes / limits

* A *locally traced* claim proves agreement of text and committed evidence, not
  correctness of the computation behind it. Bind a claim to a physics reference
  separately (that is what `docs/verification-*` cases do).
* Tree provenance is a numeric-collision test; a common round value could match
  by coincidence, which is why it is reported and not gated.
* Files whose suffix is not in `{.json,.dat,.csv,.txt}` (`.npz`, `.png`) are not
  mined; 3 `.npz` artifacts exist and are currently invisible to the audit.
* The gate only covers reports that already have colocated evidence. Raising the
  gated share requires archiving run outputs next to the report — a per-case
  change, not something this audit can do centrally.

## 7. CI-repair pass (PR #105, follow-up round)

The first round of this case was red in CI on both jobs (`test` 3.11/3.12 and
`lint`) while green on the authoring machine. Three defects, all reproducible
locally, were found and fixed here:

| # | defect | local reproduction | after fix |
|---:|---|---|---|
| 1 | `claims.json` / `traceability.json` recorded **absolute worktree paths** (`/root/tp-agent/work/m3601/docs/...`), so the archived provenance only resolves in the tree that generated it | replaying the old registry with the prefix rewritten to a CI checkout path gives `checked=0`, `violations=15`, all `doc_missing` | paths are recorded repo-relative (`repo_relative` / `repo_path`), replayed registry gives `checked=15`, `violations=0`; the whole tree copied to a different root still yields `8 passed` |
| 2 | this report quoted the M2903 reproduce script name literally, i.e. it failed its own dead-pointer gate (`dead_scripts=1`) | `test_no_report_quotes_a_missing_reproduce_script` red on `docs/verification-report-traceability/report.md` | dead name removed from prose; the detector for that case is pinned by a negative control (`test_negative_control_missing_reproduce_script_is_detected`), gate now `dead_scripts=0` |
| 3 | the summary table above is generated from the audit, but was hand-copied once and then went stale (`claimable` 1813 archived vs 1818 live) and the unused `pytest` import made `ruff` red | `test_traceability_baseline_is_recorded_and_does_not_regress` red; `ruff check` `F401` | table is rendered from `summary` by `scripts/audit_report_traceability.py --sync-report` (iterated to a fixed point, since the report quotes the audit's own totals), `ruff check src scripts tests/test_report_traceability.py` clean |

Two design notes that came out of the repair: the audit's own
`traceability.json` is **not** treated as evidence any more (binding a report's
numbers to the audit's own output would be a tautology, not provenance), and the
report table is regenerated rather than typed, so defects 1 and 3 cannot come
back silently. The physics claims of this case are unchanged: the corpus share
numbers moved only by the counts of this pass, and no bound claim went missing
(`n_claims=15` before and after).
