# CI lint job: advisory semantics belong on the steps, not the job

Status: fix applied on `agent/m3629` (PR #109).  Scope: `.github/workflows/ci.yml`
plus a regression test and this note.  No solver or verification code touched.

## 1. Symptom

PR #109 reported two red checks:

```
lint (advisory) = failure
lint (advisory) = failure
```

The duplicate is expected: the workflow triggers on both `push` and
`pull_request`, so one commit carries two check runs with the same name.  Both
were red, and both on the *advisory* job — the job that is documented as
"never block anything".

## 2. Root cause

The job expressed its advisory intent with a **job-level** flag:

```yaml
  lint:
    name: lint (advisory)
    continue-on-error: true     # <-- job level
    steps:
      ...
      - run: ruff check src tests scripts
      - run: ruff format --check src tests scripts
```

GitHub treats the two levels of `continue-on-error` differently:

| level | workflow run | job / check-run conclusion |
|---|---|---|
| `jobs.<id>.continue-on-error: true` | success | **failure** |
| `jobs.<id>.steps[*].continue-on-error: true` | success | success (step `outcome=failure`, `conclusion=success`) |

Job-level `continue-on-error` only stops the *workflow run* from failing; the
job is still published with conclusion `failure`.  Anything that gates on
check-run conclusions — here the platform's `pr-gate` bookkeeping — therefore
sees a hard red on every pull request, including purely documentary ones.

## 4. Why the red is inherited, not caused by this PR

```console
$ git diff --stat $(git merge-base origin/main agent/m3629)...agent/m3629
 docs/verification-native-kovasznay-report.md | 67 ++++++++++++++++++++++++++++
 1 file changed, 67 insertions(+)
```

PR #109 adds one Markdown report.  It introduces no Python, so it cannot have
introduced a single ruff finding: the 9822 findings and the 554 formatting
deltas are the pre-existing backlog that the workflow comment already
acknowledges ("Advisory on purpose: the tree carries a large pre-existing ruff
backlog").  Clearing that backlog — ~9.5k hand-unpacked one-liner statements
across ~550 files — is a tree-wide reformat that does not belong in a
report-only PR (it would bury the report and is not reviewable in one pass).

So the defect to fix in this PR is the *expression of advisory*, not the debt:

* intent of the job: never block on the backlog, keep the signal visible;
* actual behaviour: block every PR through the check-run conclusion.

## 5. Fix

`.github/workflows/ci.yml`, lint job only:

1. remove the job-level `continue-on-error: true` (this is what published the
   failed check run);
2. add `continue-on-error: true` to the two ruff steps, so they record
   `outcome=failure` (red step + annotation) while the job concludes success;
3. add a **Backlog snapshot** step that writes `ruff check --statistics` and
   `ruff format --check` totals into `$GITHUB_STEP_SUMMARY` — advisory must not
   degrade into invisible, and the counts are the burn-down metric for
   promoting this job to a gate;
4. document the promotion path in the job comment.

The `test` job is untouched: `Run tests` remains blocking (asserted by test).

## 6. Verification

* **Regression guard** — `tests/test_ci_lint_advisory.py` (5 tests, no new
  dependency; YAML parsing is `importorskip`).
  Positive control on the fixed workflow:

  ```console
  $ python -m pytest tests/test_ci_lint_advisory.py -q
  5 passed
  ```

  Negative control on the *previous* workflow (`origin/main:.github/workflows/ci.yml`
  dropped into a scratch tree with the same test file):

  ```console
  $ python -m pytest tests/test_ci_lint_advisory.py -q
  FAILED test_lint_job_has_no_job_level_continue_on_error
  FAILED test_ruff_steps_match_the_declared_mode
  FAILED test_backlog_stays_measurable_while_advisory
  FAILED test_workflow_parses_and_lint_job_is_advisory
  4 failed, 1 passed
  ```

  i.e. the guard fails exactly on the defect it describes.  The single passing
  test is the "test gate must stay blocking" assertion, which holds for both
  versions by design.
* **Promotion control** — the guard is mode-aware, so it does not become a
  blocker for the promotion path: the same workflow with the job renamed to
  `lint (gate)` and every `continue-on-error` flag removed yields

  ```console
  $ python -m pytest tests/test_ci_lint_advisory.py -q
  4 passed, 1 skipped
  ```

  (the skipped test is the summary requirement, which only applies while the
  job is advisory).
* **Workflow validity** — parses with PyYAML 6.0.3; `jobs = ['lint', 'test']`;
  lint steps expose `continue-on-error: true` on every ruff step and no
  job-level key.
* **Self-lint** — the two new files are clean under the same commands the job
  runs: `ruff check` → `All checks passed!`, `ruff format --check` → already
  formatted.

## 7. Promotion path (burn-down)

Advisory is a loan against future work, not a permanent exemption.  Suggested
order, each step reviewable on its own:

1. `ruff check --fix` (191 safe fixes: `F401`, `E401`, `F541`, `E703`) then drop
   those rules from the reported total;
2. mechanical `E701`/`E702` unpacking, one package per PR (`src/tensorfvm/verification`
   first — it dominates the count), each backed by the existing test suite;
3. `E731`/`F841`/`E402`/`E741` by hand, file by file, where a real defect hides
   behind the style finding;
4. `ruff format` sweep last (it rewrites everything at once, so it should land
   when `ruff check` is already clean);
5. delete the three per-step `continue-on-error` flags; the job becomes a gate.

## 8. Scope and limitations

* The fix changes which conclusion is *published*; it does not change a single
  ruff finding.  The lint signal is unchanged in content, and the backlog is
  now printed into each run summary.
* Verified locally: YAML structure, positive/negative control of the guard, and
  ruff status of the added files.  GitHub-side confirmation (the two
  `lint (advisory)` check runs turning green on the new head) can only be
  observed after the branch is pushed; no API credentials for the checks API
  were available in the work environment.
* The guard is mode-aware: it keys off the job name, so "advisory name with
  blocking steps" and "gate name with non-blocking steps" both fail, while
  either consistent state passes.  Renaming the job and removing the per-step
  flags (promotion) keeps the suite green.
